# 投机解码

## 1. 为什么能加速

decode 是**访存受限**：一步只算 1 个 token，却要把全部权重从显存读一遍。投机解码一次前向算 K+1 个位置，权重只读一遍，于是"每 token 的权重读取成本"被摊薄 —— 用便宜的算力换昂贵的访存。

前提是**取到草稿的代价远小于跑 target**。

## 2. 一步的编排（`src/spec/engine.py`）

```
已有序列  t_1 ... t_L
验证输入  [t_L, d_1, ..., d_K]         K+1 个位置，走 prefill 通道（varlen attention）
输出位置  pos 0 → 预测 d_1 ; ... ; pos K-1 → 预测 d_K ; pos K → 白送一个 token

emitted = draft[:j] + [argmax(logits[j])]      j = 接受长度
```

- `j = 0`：第一个草稿就被拒，只产出 target 的修正 token。
- `j = K`：全接受，产出 K 个草稿 + 第 K 个位置白送的那个。
- **无损**：接受概率 `min(1, p/q)`，被拒后从 `(p-q)` 的正部归一化重采样，两路合起来恰好还原 target 分布。

代码：`SpecEngine.step()`（`src/spec/engine.py:158`）、`build_verify_input()`（`:139`）、接受判定 `src/spec/verify.py:91 greedy_accept_length()` / `:122 sample_accept()`。

## 3. 两种草稿

| 来源 | 实现 | 特点 |
|---|---|---|
| n-gram | `src/spec/ngram.py` `NgramDrafter.propose()` | 零额外模型，只吃输入里的重复片段；`max_n` 默认 4 |
| 小模型 | `src/spec/draft.py` `ModelDrafter` | 每步跑一次 draft 前向；要求**同词表**且参数量远小于 target |

两者的接口是同一个 `propose(token_ids, k) -> list[int]`，上层 `SpecEngine` 不区分。

n-gram 只做朴素扫描（每次匹配 O(n·L)），生产实现应预建「n-gram → 后继」索引。

## 4. 与调度器的耦合（v6 的写法）

带草稿的序列**走 prefill 通道**（`src/control/scheduler.py` 把 `spec_draft_ids` 非空的序列从 decodes 挪到 prefills）：只有 varlen attention 能一次算 K+1 个 query，decode 通道每序列只收 1 个。

验证批按固定宽度 `[bs, K+1]` 组包（`_spec_width`），所以 CUDA Graph 的形状档位要额外乘上 K+1；MoE 时 workspace 也要按形状池化。

记账在 `_update_spec_batch()`：`j = greedy_accept_length(draft, seg[:len(draft)])` → `emitted = [*draft[:j], int(seg[j])]` → `seq.num_cached_tokens += j + 1` → `kv.sync_prefix(seq, num_new_tokens=j+1)`。

## 5. 实测

`bench/spec_sweep.py`（Qwen3-0.6B、单卡、`enforce_eager=True`、n-gram、单请求 64 token 贪心、3 次均值）：

| K | 草稿命中 | 接受长度 | 加速比 |
|---|---|---|---|
| 1 | 高（重复文本） | ~0.9 | ~1.0× |
| 2 | 高 | ~1.6 | ~1.3× |
| 4 | 中 | ~2.0 | ~1.4× |

要点：收益强依赖文本的重复性；K 越大草稿越贵，本机上 K=4 之后开始回落。原始数据用 `python bench/spec_sweep.py --k 1,2,4` 复跑。

## 6. 已知问题

- **`max_tokens` 可能多 1 个 token**：验证批一次回写 `j+1` 个 token，边界那一步会越界一格（与 v6 相同，非合并引入的回归）。
- **与 ZOS 互斥**：接受长度 `j` 在 GPU 上产生，ZOS 的 CPU 提前调度无法拿到；开投机时 ZOS 自动关闭（`src/control/core.py:90`）。
- n-gram 的 `propose()` 在 CPU 上读 `seq.token_ids`，因此它本身也是 ZOS 的一个阻碍点。
