# 基准与复现

## 0. 硬件与口径

- 本机：RTX 3050 Laptop **4 GB**、Qwen3-0.6B、**无 flash-attn**（走 `_flash_attn_fallback.py` 的 SDPA 回退）。
- 这套硬件上限很低（一步 130–170 ms，GPU 只忙 15.6 ms），**所有"没有加速"的结论都是它造成的**，不代表机制无效。
- 报数三要素：模型 / 硬件 / 并发。下面每个数都标了这三项。
- **没有在 4090 / A100 / H100 上实测过**：本仓库所有数字都出自上面这张 3050。
  §7 给的是"换机器怎么复现"的步骤，不是别处的实测结果。

## 1. 正确性对拍

```bash
bash bench/final.sh /tmp/final.txt
```

三组场景，ZOS 两模式各跑一次，**逐 token 完全一致**：

| 场景 | steps（ZOS=0 / 1） | token sha |
|---|---|---|
| short n=4 16 tok blocks=32 | 16 / 17 | `ccdcef6fb73a` |
| chunk n=1 101 prompt tok max_batched=64 | 9 / 11 | `22fd17881826` |
| short n=8 8 tok blocks=24 prefix=hash | 8 / 9 | `09cfd5296a19` |

ZOS 多 1 步是收尾（最后一批在途请求要 flush 一次），不影响产出。

合并进 `kritace_vllm` 后的冒烟对拍（2 请求 × 8 token，blocks 24）：`KRITACE_ZOS=0` → `steps=8 sha=217a996c7934`；`=1` → `steps=9 sha=217a996c7934`。

## 2. 机制指标（证明"等"消失了）

```bash
KRITACE_ZOS_STATS=1 KRITACE_ZOS=0 python bench/zos_matrix.py --case short --n 8 --max-tokens 32 --blocks 48
```

`_note_ready()` 先 `event.query()` 再 `synchronize()`，只统计真正等待的时间：

| n=8 / 32 tok | ready 比例 | 累计等待 | 平均 |
|---|---|---|---|
| ZOS=0 | 1/32（3.1%） | 56.8–76 ms | 1.78 ms/步 |
| ZOS=1 | 32/32（100%） | 0.1–0.3 ms | 0.005 ms/步 |

`nsys` 交叉验证（`bench/nsys_zos.sh`）：`zos.read` 区间 ZOS=0 中位 1728 µs、ZOS=1 中位 36 µs。

## 3. 气泡（B）有多大

```bash
KRITACE_ZOS_GPU=1 python bench/repro_zos.py --rounds 3          # cudaEvent 探针，交错跑
python bench/cpu_bubble.py                                       # 分相计时
```

| 方法 | ZOS=0 | ZOS=1 |
|---|---|---|
| 步墙钟 − GPU 忙时（n=8） | 131.52 − 131.23 = **0.29 ms** | 133.56 − 133.56 = **0.00 ms** |
| 分相求和（bs=8） | schedule 0.030 + to_wire 0.010 + build 0.161 + finish 0.029 ≈ **0.23 ms** | — |
| 分相求和（bs=32） | ≈ **0.33 ms** | — |

**一个 decode 步只有一个气泡**（整批只发射一次前向），不随并发数增加；并发越大 `G` 越长、`B/G` 越小。

## 4. 为什么端到端量不出加速

```
T = G + B     加速比 = 1 + B/G
```

本机一步约 130 ms，其中 GPU 真正在算只有 15.6 ms（其余是 CPU 提交 kernel 的时间，即 CPU launch-bound），`B ≈ 0.23 ms` ⇒ `B/G ≈ 0.2%`，落在 ±7% 的噪声里。

注入 100 ms `sleep` 的反证：ZOS=1 也完整付了 100 ms —— 流水线里没有可叠的窗口，因为回退 attention 里每层一次 `.tolist()` 让 CPU 与 GPU 锁步。

换到真 flash-attn + CUDA Graph：`G` 降到 1.5–10 ms、`B` 不变 ⇒ 收益 2% 到 15%（`bench/cpu_bubble.py` 的量测 + `1+B/G` 推算，非实机数据）。

`bench/gap_step.py` 从 nsys sqlite 算**步边界**的 GPU 空转：本机 0.005 ms（27/27 步 < 0.05 ms）—— 因为 CPU 提交慢于 GPU 执行，GPU 永远追不上队列，步边界自然不空。等 launch 成本降下来，这个脚本才量得出 ZOS 的功劳。

## 5. 测量方法与防坑

| 坑 | 做法 |
|---|---|
| 墙钟噪声 ±7%，效应 0.2% | 取中位数、丢 warmup、两模式**交错**跑（A B A B） |
| 把 GPU 降频误判成加速 | **双指标交叉校验**：墙钟变快必须 GPU 忙时不变；n=32 那次 227.6→208.2 ms 的"8.5% 加速"就是 GPU 忙时也从 227.0 掉到 213.6，判为假阳性 |
| 单次数字不可信 | 先量化噪声，效应小于噪声就不宣称显著 |
| 分相计时的绝对精度 | ±10%；event 相减只有 1 位有效数字，只用于判量级 |

## 7. 在别的机器上复现

要求：CUDA **cu12x** + `flash-attn >= 2.5`（`flash_attn_with_kvcache` 的分页 KV 是 2.5 才有的）。装好后：CUDA Graph 能开、`G` 会掉到毫秒级、`B/G` 才看得出来。

注意事项：

- **跨机 token sha 不保证一致**（不同 cuBLAS / flash-attn 版本会翻转 token）。真正的不变量是**同一台机器上 ZOS=0 与 ZOS=1 逐 token 一致**。
- 云端实例常被限功耗，先 `nvidia-smi -q -d CLOCK` 确认没降频，再对比数字。
