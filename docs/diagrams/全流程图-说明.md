### 0.1 每一格都是上下两行：**上行写逻辑，下行写等式**

这是照 `InfiniLM .../tp_pp_4gpu.html` 的排版做的：

```
┌──────────────────────────────────────────────┐
│ ③ 查表得向量：词表并行，越界 token 取零向量      │  ← 上行：这一步在干什么
│ h[N,hs] = E[x],  hs=1024,  V=151936           │  ← 下行：它的等式（带维度）
└──────────────────────────────────────────────┘
```

> 实现上是把整格写成一个 `$$\begin{gathered} … \end{gathered}$$`：
> 第一行 `\text{…}` 是逻辑，后面几行是公式。
> **不能用 `<br/>`** —— 标签里一旦出现 `$$`，mermaid 就不再处理 `<br/>` 了。

### 0.2 卡号只写在**列标题**上，格子里不重复

列标题写一次就够了：

> **卡 0 · 段 0 · TP rank 0　（跑层 0–13；负责 Q 头 0–7、KV 头 0–3）**

格子里面只写「收到本步入参」「③ 查表得向量」这种**这一步在干什么**，不再每格都缀一个「卡 0 ·」。

### 0.3 竖着读一遍：主图的完整顺序

主图不是一堆并列的卡片，而是**一条从上到下的线**，共 12 段：

| 顺序 | 段 | 在哪跑 | 一句话 |
|---|---|---|---|
| 1 | `HOST` ① 引擎层 | CPU · 进程 0 · 卡 0 | 选这一轮算谁；开着投机就先去出草稿 |
| 2 | `SP1` ⑰ 投机上半场 | CPU · 卡 0 | 先算划不划算 → 出草稿 → 构造验证输入 → **按 K+1 占账本** |
| 3 | `H1` 交接①（橙） | CPU → GPU | 六张表异步拷进显存，**拷完立刻返回、不在这里等** |
| 4 | `SHP` 三种形状 | —— | 说明块：prefill / decode / 投机验证是同一条路径的三种形状 |
| 5 | **卡 0 ⇄ 卡 1**（段 0） | GPU | 两张卡各跑 13 步，中间夹三次跨卡求和 |
| 6 | `X3` 段边界下发 | GPU → GPU | 卡 0 → 卡 2、卡 1 → 卡 3，送 `h` 与 `r` **两项** |
| 7 | **卡 3 ⇄ 卡 2**（段 1） | GPU | 与段 0 同一套，末段多一个采样 |
| 8 | `RET` 回程（橙） | GPU → CPU | 异步拷回 token 号 → 同步等 → 走控制通道交给 driver |
| 9 | `SP2` ⑰ 投机下半场 | CPU · 卡 0 | 判接受 → 重采样 → **账本只推进 j+1** |
| 10 | `UPD` 收尾 | CPU · 卡 0 | 判结束 → 发布满块 → 抢占 → 防死循环 |
| 11 | `H6` 交接⑥（橙） | CPU → 外部 | 每步都把新多出来的 token 流出去 |
| 12 | 回流 | CPU 触发 GPU | 下一步的输入，回到第 1 段 |

> **橙色框 = CPU 与 GPU（或 CPU 与外部）的交接**，**蓝色框 = 卡与卡之间的通信**。见 §1.5。

### 0.4 四张卡各自的一条流程（这就是主图的全部内容）

| 列 | 是谁 | 自己那条流程（每列 13–14 步，格子里的公式各不相同） |
|---|---|---|
| **卡 0** | 段 0 · TP rank 0（Q 头 0–7、KV 头 0–3） | 收输入 → ③ 查表 →〔**通信**：查表求和〕→ ④-1 归一化① → A1 三合一投影（取**前半段**）→ A2–A4 拆头 / 头内归一化 / 位置编码 → A5 写自己的 KV → A6–A9 注意力（本卡 8 个头）→ A10 输出投影（**部分和**）→〔**通信**：第 1 次求和〕→ ④-3 残差① + ④-4 归一化② → B4 路由 → B5–B7 自己的专家分片（**部分和**）→〔**通信**：第 2 次求和〕→ ④-6 残差② → 14 层跑完发出 |
| **卡 1** | 段 0 · TP rank 1（Q 头 8–15、KV 头 4–7） | 与卡 0 **同一套步骤**，只是取**后半段**、头号不同 |
| **卡 2** | 段 1 · TP rank 0（**末段，采样只在卡 2**） | 收卡 0 的 h,r → ④-1 … ④-6（同一套）→ 末层归一化 → lm_head 出 logits → **采样出 token 号 → 回传卡 0** |
| **卡 3** | 段 1 · TP rank 1（**不采样**） | 与卡 2 **同一套步骤**，最后一步只写「本卡不采样，等下一轮」 |

**卡与卡之间的通信框**（蓝底，单独一组，排在两张卡的中间）：

| 框 | 是谁和谁 | 送什么、算出什么 |
|---|---|---|
| ③ 查表求和 | 卡 0 ⇄ 卡 1 | 越界 token 在别的卡上是零向量，`h = Σ_r h⁽ʳ⁾` |
| 层内第 1 次求和 | 卡 0 ⇄ 卡 1 | 输出投影的部分和，`y = y⁽⁰⁾+y⁽¹⁾` |
| 层内第 2 次求和 | 卡 0 ⇄ 卡 1 | 专家分片的部分和，`m = m⁽⁰⁾+m⁽¹⁾` |
| 层内第 1 / 2 次求和 | 卡 2 ⇄ 卡 3 | 与段 0 同一套，只换了一对卡 |
| PP 边界下发 | 卡 0 → 卡 2、卡 1 → 卡 3 | **两项**：`h[N,hs]` 与 `r[N,hs]` |
| **⚠ 没有「PP 回传」** | —— | 段边界点对点**只有正向**（段 0 → 段 1），送的是隐层与残差两项。采样出的 token 号**不走这里**，走 CPU 上的**控制通道**（只传字节、用 Gloo），见 §1.5 |

> 把两列都摆出来才能"看见"并行 —— 只写一句"卡 0 与卡 1 各算一半"是看不出过程的。

## 1. 怎么读这张图

### 1.1 读法：先看列，再看列与列之间的横框

```
最上面那个框 = ① 引擎层（CPU / 进程 0 / 卡 0）：决定这一轮算谁、把输入拼成表
     ↓ 四张卡拿到同一批入参
┌─── 卡 0（左列）─────┐          ┌─── 卡 1（右列）─────┐
│ 收输入 → 查表 → …   │ ⇄ 通信框 ⇄ │ 收输入 → 查表 → …   │   ← 段 0：跑层 0–13
└────────────────────┘          └────────────────────┘
     └────────── PP 边界下发（h 与 r 两项）──────────┘
┌─── 卡 2（左列）─────┐          ┌─── 卡 3（右列）─────┐
│ 收上一段 → … → 采样  │ ⇄ 通信框 ⇄ │ 收上一段 → … → 不采样│   ← 段 1：跑层 14–27
└────────────────────┘          └────────────────────┘
     ↓ 采样出的 token 号：不在卡间直传，先异步拷回 CPU，再走控制通道交回最上面那个框（闭环）
```

**一条竖着读下来的列 = 一张卡自己的一整条流程**；
**列与列之间横着的蓝框 = 这两张卡必须一起走到的通信点**。

凡是 allreduce，**两张卡各自发起同一条、算完各自都有一份完整结果**（没有主卡）。

| 样式 | 含义 |

| 颜色 | 是什么 | 有哪几处 |
|---|---|---|
| **橙色**（`:::io`） | **CPU 与 GPU / CPU 与外部之间的交接** | `H1` 下发（①）、`H2` 回传（②）、`H3` 同步点（③）、`H4` 控制通道、`H6` 流出（⑥） |

## 3. 主干：真实形状与公式

模型是 **Qwen3-0.6B**（dense）与 **Qwen1.5-MoE-A2.7B**（MoE）两套，图上凡有差别处都标了。

### 3.1 每层骨架（28 层共用）

$$
h = x + \mathrm{Attn}\big(\mathrm{RMSNorm}_1(x)\big),
\qquad
x' = h + \mathrm{FFN}\big(\mathrm{RMSNorm}_2(h)\big)
$$

$$
\mathrm{RMSNorm}(x) = \frac{x}{\sqrt{\frac{1}{d}\sum_i x_i^2 + \epsilon}} \odot \gamma,
\qquad \epsilon = 10^{-6}
$$

三个要点：

- **残差是 fused 的**：`RMSNorm` 吃 `(h, res)` 吐两个值（归一化后的输入 + 更新后的残差），少一趟显存读写；
  代价是 residual 必须一路传下去 —— **PP 段间传的也是两项**（`IntermediateTensors(hidden_states, residual)`）；
- 注意 `h = x + Attn(...)` 里 **`Attn` 的输入是归一化后的 `x`**（pre-norm），不是 `Attn(x) + x`；
- 字段名叫 `*layernorm`，但**全是 RMSNorm**（没有均值、没有 bias）。

### 3.2 出口

| 步骤 | 形状 | 说明 |
|---|---|---|
| 末层 `norm` | `[N,1024]` | 全模型唯一，**只在末 PP 段存在**（其它段是 `PPMissingLayer`） |
| `lm_head` | `[N,1024] → [n,151936]` | 只对**需要的位置**算：decode 1 个 / prefill 每序列最后 1 个 / 投机全部 `K+1` 个 |
| 采样 | `[n]` | `softmax(z/T)` → top-k → top-p → min-p；`all_greedy` 时直接 argmax |

⚠️ **prefill 算了一整段的 logits，但只有每序列最后一个位置有用**（`last = cu_seqlens_q[i+1] − 1`）。
投机验证是唯一"要用中间位置"的通道 —— 因为每个草稿位置都要和 target 的 argmax 比一次。

## 4. 四条通道：同一条模型路径的四种形状

`RF`（`ModelRunner.run_forward`）按 `(is_prefill, 是否开 CG/compile)` 分派到四条路：

| 通道 | 条件 | 走什么 |
|---|---|---|
| `CG` | decode 且 `enforce_eager=false` 且 `bs ≤ max_bs` | `cuda_graph_runner.replay(bs)`，按 `_pad_bs` 填到固定形状，pad 槽 `slot = −1` |
| `EG` | decode 且不满足上面 | `eager self.model(...)` |
| `CP` | prefill 且 `num_cached_tokens == 0` 且 `torch_compile=true` | `prefill_fn(...)`，**只有首 chunk 走编译** |
| `EP` | 其余 prefill（含投机验证） | `eager varlen self.model(..., cu_seqlens_q/k, block_tables)` |

⚠️ **`RF` 是"先 decode、后 prefill"**（`run_forward` 就是这么写的），回写 `update()` 也是同序 ——
两边共用同一个 `ScheduledBatch`，顺序不一致就会"token 与序列对错位"。

## 5. 注意力子层（`AT1`–`ATA`）

$$
\text{attn} = \mathrm{softmax}\!\left(\frac{QK^\top}{\sqrt{d_h}} + \text{mask}\right)V,
\qquad d_h = 128,\quad H_{kv} = \lfloor H/G \rfloor,\ G = 16/8 = 2
$$

| 步骤 | 操作 | 形状 |
|---|---|---|
| `AT1` | `qkv_proj` 融合 GEMM（ColumnParallel） | `[N,1024] → [N,4096]`（2048 + 1024 + 1024） |
| `AT2` | split + view 拆头 | q `[N,16,128]`、k/v `[N,8,128]` |
| `AT3` | `q_norm` / `k_norm` | `RMSNorm(128)`，归一化轴是 **head_dim**（Qwen3 的 QK-Norm） |
| `AT4` | partial RoPE | 只转 q、k，**v 不旋转**；`rope_theta = 1e6` |
| `AT5` | **写 KV cache** | `store_kvcache(k, v, k_cache, v_cache, slot_mapping)`；`slot == −1` 直接 `return` |
| `AT6` | 分岔 | prefill/投机 → `AT7`；decode → `AT8` |
| `AT7` | `flash_attn_varlen_func(causal=True, block_table=…)` | 有 cache 时 K/V **直接取整池** |
| `AT8` | `flash_attn_with_kvcache(q.unsqueeze(1), …, cache_seqlens, block_table)` | 每序列只接受 **1 个** query |
| `AT9` | GQA 8 → 16 头 | 由 FA 内部取，**不复制、不入缓存** |
| `ATA` | `o_proj`（RowParallel） | `[N,2048] → [N,1024]`，down 侧 allreduce |

四个容易写错的点：

- **$16\times128 = 2048 \ne$ hidden 1024**：注意力是**升维**的；`head_dim` 是 config 显式给的 128，**不是** `1024/16 = 64`；
- **`AT5` 在注意力之前**：新 token 的 K/V **先写进池子**，注意力才能（prefill 有 cache 时）从整池读 —— 这也正是**投机验证能走这条路**的原因；
- **缓存里存的是 8 头**（GQA 复制只服务当次计算）；把复制后的 K/V 写回缓存会让显存翻倍，且 decode 形状对不上；
- **为什么 decode 不走 varlen**：`flash_attn_with_kvcache` 每序列只接受 1 个 query；投机验证一次要 `K+1` 个，所以调度器把有草稿的序列**从 decode 通道挪进 prefill 通道**（图上的 `E6`）。

## 6. 前馈子层：两条分支

两条分支的**外框完全一样**（都是"升维 → 非线性 → 降维"），差别只在中间：
**是"一个"FFN，还是"很多个 FFN 里挑几个加权"。**

### 6.1 分支 A：dense MLP（SwiGLU）

$$
\mathrm{FFN}(u) = W_{\text{down}}\Big(\underbrace{\mathrm{SiLU}(W_{\text{gate}}u)}_{\text{门}} \odot \underbrace{W_{\text{up}}u}_{\text{值}}\Big),
\qquad \mathrm{SiLU}(z) = z\,\sigma(z)
$$

| 步骤 | 操作 | 形状 |
|---|---|---|
| `A1` | `gate_up_proj`（gate 与 up **融合成一次 GEMM**） | `[N,1024] → [N,6144]`（2×3072） |
| `A2` | `SiluAndMul` | `[N,6144] → [N,3072]` |
| `A3` | `down_proj`（RowParallel） | `[N,3072] → [N,1024]` |

**融合的收益**：两个投影的输入是**同一张** `u`，拼成一次 GEMM 就同时出两半 ——
少一次 kernel launch、少读一遍 `u`（decode 是访存瓶颈，这是纯赚）。

⚠️ **`SiLU` 是激活函数，`SwiGLU` 是用 SiLU 做门的 FFN 结构** —— 两者不是一回事。

### 6.2 分支 B：MoE

$$
\begin{aligned}
s &= \mathrm{softmax}(W_{\text{router}}\,u) && \text{（每个专家一个分数，fp32）}\\
\mathcal{T} &= \mathrm{TopK}(s,\ k) && \text{（只留 k 个：本仓库 MoE 模型 k=4，共 60 专家）}\\
w_i &= \frac{s_i}{\sum_{j\in\mathcal{T}} s_j},\quad i\in\mathcal{T} && \text{（★ 只在选中的里面重新归一化）}\\
\mathrm{FFN}_{\text{MoE}}(u) &= \sum_{i\in\mathcal{T}} w_i\, F_i(u) && \text{（每个 }F_i\text{ 就是 6.1 的 SwiGLU，权重不共享）}
\end{aligned}
$$

三个要点：

1. **`B2` 的"重新归一化"不能省**：只留 top-k 之后它们的和一般 $\ne 1$，不重新归一化整体输出幅度就不对（手撕 MoE 最爱考这一点）；
2. **`B3` 是"同一段代码跑几遍"**：每个专家是**独立的** 6.1 那种 FFN，只是权重不同 —— 所以"几个专家放一张卡"就成了切分问题（§8 的 EP）；
3. **`B4` 的"加权"与 §3.1 的"残差"不是一回事**：`B4` 的权重来自路由，残差是恒等式的加法。

## 7. 两套缓存（`CACHE`）

| | 数据在哪 | 账本在哪 | 内容 |
|---|---|---|---|
| **KV 池** `C1` | ⓖ GPU | ⓒ CPU | `pool[2, 28, num_blocks×256, 8, 128]` |
| **块管理** `C2` | ⓒ CPU | ⓒ CPU | `BlockManager` / `KVManager` / 前缀缓存（`none`/`hash`/`radix`） |

$$
\text{KV bytes/token} = \underbrace{2}_{K,V} \times \underbrace{L}_{28} \times H_{kv} \times d_h \times \text{sizeof(dtype)}
= 2\times28\times8\times128\times2\text{B} = 112\ \text{KiB}
$$

| 项 | 每 token / 每层 | 每 token（28 层） | 一条 4096 上下文 |
|---|---|---|---|
| KV cache | $2\times8\times128\times2\text{B} = 4$ KiB | **112 KiB** | **448 MiB** |
| 一个块（`block_size 256`） | 256 × 4 KiB = 1 MiB | 28 MiB / 块 | — |

> 默认 `max_num_seqs = 256`：若每条都满 4096 上下文，KV 上限 $256 \times 448\ \text{MiB} \approx 112\ \text{GiB}$ ——
> **远超单卡显存**。实际可用条数由 `num_kvcache_blocks`（`0` = 按 `gpu_memory_utilization 0.85` 自动算）
> 与并发长度共同决定。**这就是"必须按块管理、必须有前缀缓存"的算术原因。**

**块管理三条规则**（`C3`）：

| 规则 | 为什么 |
|---|---|
| **满块才进索引** | 半截块的内容下次还可能变（再来一个 token 就写进去了），进索引会让别人命中错前缀 |
| **抢占 = `deallocate(publish=False)` + 丢草稿** | 本仓库没有 SWAP 态、只有 recompute；抢占时**不发布**。⚠️ 必须把 `spec_draft_ids` 一并丢掉，否则序列带着 decode 语义的草稿回到 waiting，重新 prefill 时草稿长度与已缓存前缀对不上 |
| **`release_to_cached_or_free`** | 块是"归还给缓存"还是"直接释放"，取决于它有没有完整的身份（hash / 前缀键） |

## 8. 四种并行轴（主图四列 + 中间蓝框；总表在 `说明区.html` ⑬ 段）：多卡时多出来的东西

### 8.1 一张判据表（这是全篇最该背的一句）

> **求和（收缩）轴被切 ⇒ 部分和 ⇒ 必须归约；切输出维 ⇒ 完整切片 ⇒ 零通信。**

| 并行 | 切什么 | 每卡拿到 | 要不要通信 |
|---|---|---|---|
| **TP 列并行** | 输出维（`qkv_proj` / `gate_up_proj`） | **完整切片** | ❌ 零通信 |
| **TP 行并行** | 输入维（`o_proj` / `down_proj`） | **部分和** | ✅ allreduce |
| **PP** | 层（`get_pp_indices`） | 一段层 | ✅ 段间 send/recv |
| **DP** | 样本（`dp_size` 个独立 Engine） | 完整模型副本 | ❌ 副本间无通信 |
| **EP** | 专家轴（`enable_ep=true`，在**现有 TP rank 上**切，不扩大 world） | 部分专家 | ✅ allreduce |

### 8.2 各并行轴的真实数字

**TP**（`X1`/`X2`）：

- **集合通信没有"主卡"**：每张卡各自发起同一条 allreduce，相加由集合通信在**各卡自己的设备上**完成；
- **每层 allreduce 次数：2 次**（这是核对过源码的，别记错）：
  ① `o_proj`（注意力输出投影，行并行）② 前馈的输出投影（稠密是 `down_proj`，MoE 是专家合并）。
  算一次前向总共 **2 × 28 + 1 = 57 次**（那个 +1 是 embedding 输出，词表并行，每步一次，不在层内）。
  ⚠️ **没有"全局方差归一化"那一次** —— 那是另一个项目（MiniMax Lightning 层）的设计，
  本项目两个归一化（层入口 / 注意力后）都作用在**完整 hidden** 上，每个 rank 都有一份完整输入 ⇒ **零通信**；
  头内归一化作用在 128 维的头上、只碰本卡的头 ⇒ 也是零通信。
- 实测（2× RTX 4090D，无 NVLink，P2P NS）：allreduce 延迟 8 KB = **76.7 µs**，
  Qwen3-0.6B 每步 $\approx 8\,\text{KB} \times 2 \times 28 = 224$ KB ⇒ 通信串行 $\approx 2.15$ ms；
- ⇒ **只有单层计算时间 > 单层 AR 通信时间时 TP 才划算**。0.6B 在 4090 上单层计算远小于 120 µs 量级，
  所以 **TP 在这台机器上注定不划算**：eager 下 TP=2 **37.9** vs 单卡 **49.5** tok/s（**−23%**）。

**PP**（`X3`）：

- 段间传 `IntermediateTensors(hidden_states, residual)` —— **两项**，不是一项；
- **lockstep 串行，不是 1F1B** ⇒ 前一段没算完后一段只能等着，**气泡随 stage 数增加**；
- 实测：eager 下 PP=2 **79.9** vs 单卡 49.5（**+61%**，因为每卡层数减半、batch=1 没有气泡）；
  但 **CG 下 PP=2 336.6 相对单卡 449.7 只有 0.75×** —— CG 一开 PP 的优势就没了；
- ⇒ **PP 买的是容量、不是速度**（装不下才用）。

**DP**（`X4`）：

- `dp_size` 个**独立 Engine 副本**，前端只维护**镜像 Sequence**，按回传增量自行推进；
- 通道是 ZMQ IPC + msgspec 而非 HTTP；`step` 阻塞等任意一路、再非阻塞收齐其余；
- 实测（0.6B，reqs=32，共 4096 token）：dp1 eager 710.0 → dp2 **1331.4**（**1.88×**）；
  cg 下 4784.3 → **8260.2**（**1.73×**）；
- ⚠️ **必须主动报出的三条边界**：**DP 不省显存、不降延迟**（单条延迟 = 单卡延迟，降延迟要 TP）、
  **收益完全依赖"并发数 ≥ 副本数"**、**卡必须同构**（环境 A 的 4090+4070 让 DP=2 掉到 **0.80×**）。

**EP**（`X5`）：

- **EP 也要 allreduce** —— 切了专家之后每卡只有**局部和**（一个 token 的 top-k 可能分散在多卡）；
  而且通信量与 MoE-TP **一样是一份 `[T,H]`**；
- **EP×CG 有负交互**：cg 下 201.04 → 161.33 tok/s（**−19.8%**）；但 eager 下方向**相反**（29.29 → 30.01，**+2.5%**）
  ⇒ 准确说法是「**不是 EP 慢，是「EP × CG」这个组合负**」；
- 处理：追吞吐且卡少 ⇒ **不开 EP + 开 CG**；装不下才开 EP。

### 8.3 为什么 CG 是 decode 的最大杠杆

实测（Qwen3-0.6B，单卡 4090D）：

| 模式 | decode (tok/s) | 倍数 |
|---|---|---|
| eager | 49.5 | 1.00× |
| **cg** | **449.7** | **9.1×** |
| compile | 50.3 | 1.02× |
| cg+compile | 446.8 | 9.03× |

**CG 消掉的是 decode 每步里与计算量无关的固定 kernel launch 开销**（参数校验 / 驱动提交 / 命令编码入队 /
CPU-GPU 传输 / PyTorch dispatch），以及 **kernel 之间的空隙**。

⚠️ **口诀：CUDA Graph 减「提交次数」，融合减「kernel 个数」** —— 说反了等于不懂 CG 到底省什么。

## 9. v6 投机解码：接受 / 拒绝规则（`说明区.html` ⑫ 段）

**这是投机解码唯一的面试考点，也是"为什么无损"的全部内容。**

### 9.1 规则

设 target 分布 $p$、draft 分布 $q$、草稿采出 $\tilde{x}$：

$$
\text{以概率 } \min\!\left(1,\ \frac{p(\tilde{x})}{q(\tilde{x})}\right) \text{ 接受};
\qquad
\text{被拒后从 } p'(x) = \frac{\max(0,\ p(x)-q(x))}{\sum_{x'}\max(0,\ p(x')-q(x'))} \text{ 重采样}
$$

### 9.2 为什么这样就对了

要证的是：经过"采样 → 可能接受 → 可能重采样"后，最终输出的 token 服从 $p$。
对任意 token $x$，最终输出 $x$ 有**两条互斥的路径**：

**路径一（草稿采到 $x$ 且被接受）**：

$$
q(x)\cdot\min\!\left(1, \frac{p(x)}{q(x)}\right) = \min\big(q(x),\ p(x)\big)
$$

> ★ **$q(x)$ 乘进去正好把 $q$ 消掉** —— 这就是 $\min(1,p/q)$ 这个看似奇怪的式子存在的唯一理由：
> 它让"接受"这一路的概率**只取决于 $\min(p,q)$，与草稿自己的分布 $q$ 无关**。
> 如果接受概率不是 $p/q$ 而是别的（比如常数 $\alpha$），乘完会剩下 $q$ 的因子，还原不出 $p$。

**路径二（草稿被拒，再从 $p'$ 采到 $x$）**：拒绝总概率是 $1-\sum_{x'}\min(q,p)$，而

$$
\sum_{x'}\max\big(0,\ p(x')-q(x')\big) = 1-\sum_{x'}\min\big(q(x'),p(x')\big)
$$

（恒等式：$\max(0,p-q)+\min(p,q)=p$ 逐项成立，两边对 $x'$ 求和，左边第二项和 $=1$。）代入：

$$
\Big(1-\sum_{x'}\min(q,p)\Big)\cdot p'(x) = \max\big(0,\ p(x)-q(x)\big)
$$

> ★ **归一化分母恰好等于拒绝概率**，所以约掉了 —— 这不是巧合，是同一个恒等式在两边。

**两路相加**：

$$
\min\big(q(x), p(x)\big) + \max\big(0, p(x) - q(x)\big) = p(x)
$$

分两种情况看就一目了然：

- $p \ge q$：接受概率 $\min(1,p/q) = 1$ ⇒ **必接受**，贡献 $q$；残差 $p-q$ 补上差额 ⇒ 合计 $p$ ✓
- $p < q$：贡献 $q\cdot(p/q) = p$，已经够了；残差 $\max(0,p-q) = 0$ ⇒ 合计 $p$ ✓

**草稿"过度自信"（$q>p$）的部分被接受概率自动砍掉，草稿"漏掉"的部分（$p>q$）由重采样补上。
一砍一补，$q$ 被完全消掉。**

### 9.3 真数字走一遍

$p = [0.6, 0.3, 0.1]$、$q = [0.3, 0.6, 0.1]$：

| token | $p$ | $q$ | 接受贡献 $\min(q,p)$ | 残差 $(p-q)^+$ |
|---|---|---|---|---|
| A | 0.6 | 0.3 | 0.3 | **0.3** |
| B | 0.3 | 0.6 | **0.3** | 0 |
| C | 0.1 | 0.1 | 0.1 | 0 |
| 合计 | 1.0 | 1.0 | **0.7** | **0.3** |

- 草稿采 A（概率 0.3）：$\min(1, 0.6/0.3) = 1$ → 必接受，贡献 **0.3**
- 草稿采 B（概率 0.6）：$\min(1, 0.3/0.6) = 0.5$ → 贡献 $0.6\times0.5 =$ **0.3**
- 拒绝总概率 $1-0.7 = 0.3$，$p'(A) = 0.3/0.3 = 1$ → 贡献 **0.3**
- 汇总 $P(A) = 0.3+0.3 = \mathbf{0.6} = p(A)$ ✓

> 💡 $q(B) = 0.6 > p(B) = 0.3$ 时接受概率只有 0.5 —— **草稿"过度自信"的部分必须被砍掉**，
> 这是分布正确性的关键。

### 9.4 三个必答的边界

| 边界 | 正确说法 |
|---|---|
| **$q$ 从哪来** | **必须来自草稿侧**。若偷懒拿 target 自己的概率当 $q$，则 $q \equiv p$、$\min(1,p/q) \equiv 1$ ⇒ 草稿被**无条件接受**、重采样那半永远不触发 ⇒ 退化成"有偏解码"（n-gram 时就偏向复读历史片段） |
| **确定性草稿（n-gram）的 $q$** | 取 **one-hot**：接受概率 $= \min(1, p(\tilde{x})/1) = p(\tilde{x})$（target 有多认可就多大概率接受）；被拒后残差 = 把 $p$ 里 $\tilde x$ 那一项抠掉再归一化 |
| **贪心（$T=0$）** | $p$、$q$ 都退化成 one-hot ⇒ $\min(1,p/q)$ 只会是 0 或 1 ⇒ 规则退化为「**草稿 token 是否等于 target 的 argmax**」，实现上可直接比 token id |

⚠️ **"同温度同截断"是正确性问题，不只是效率问题**：两边必须描述同一个"被采样的分布"
（同温度 + 同截断 + 同归一化），否则 $p$ 和 $q$ 不是在比同一个东西，9.2 的收口就不成立。

## 10. 投机解码的工程口径（实测数字）

> ⚠️ **引用投机的加速比必须注明输入文本** —— 收益完全由文本自身的重复度决定。

**本仓库 v6**（Qwen3-0.6B，单请求 64 token，eager，n-gram 草稿）decode 吞吐：

| 提示词 | K=0 | K=3 | K=5 | K=8 |
|---|---|---|---|---|
| 高重复（问答模板） | 48.7 (1.00×) | 151.3 (3.10×) | 182.6 (3.75×) | **285.9 (5.87×)** |
| 自然散文 | 49.9 (1.00×) | 74.5 (1.49×) | 82.1 (1.64×) | 87.6 (1.75×) |
| 代码 | 50.4 (1.00×) | 58.8 (1.17×) | 58.4 (1.16×) | 58.6 (1.16×) |

**5.87× ↔ 1.16×，相差 5 倍。** 代码文本 K=3/5/8 基本无差别 —— 盲目加大 K 没有意义。

**接受率与每步期望产出**（单请求 256 token）：

| 文本 | 指标 | K=1 | K=2 | K=4 | K=6 | K=8 |
|---|---|---|---|---|---|---|
| 高重复 | $\alpha$ | 1.000 | 1.000 | 1.000 | 0.991 | 0.983 |
| 高重复 | $E$ | 2.00 | 3.00 | 5.00 | 6.81 | 8.40 |
| 自然散文 | $\alpha$ | 0.950 | 0.939 | 0.894 | 0.825 | 0.835 |
| 自然散文 | $E$ | 1.95 | 2.82 | 4.05 | 4.23 | 4.86 |
| 代码 | $\alpha$ | 0.858 | 0.841 | 0.668 | 0.552 | 0.598 |
| 代码 | $E$ | 1.86 | 2.55 | **2.61** | 2.20 | 2.46 |

- 高重复：$\alpha \approx 1$ ⇒ $E$ 随 $K$ **线性增长**（每步吃满 $K+1$）；
- 自然散文：$E$ 单调增但**斜率快速下降**（K=4→8 只从 4.05 到 4.86）；
- **代码：K=4 就是拐点**（$E = 2.61$ 峰值，K=6 掉到 2.20）—— 草稿变长后"命中率下降 + 验证成本上升"双重作用。

**TTFT 是明确的负收益**（官方 vLLM 0.30.0，8B target + 0.6B draft，K=5，CG）：

| | TTFT | decode |
|---|---|---|
| 基线（无投机） | **27.31 ms** | 59.3 tok/s |
| 投机 + 真实文本 | **73.27 ms** | **128.1 tok/s** |
| 对比 | **2.68× 变差** | **2.16×** |

**为什么首步必然更贵**：无论这一回合接受多少（哪怕 $\alpha = 1$），都要先付 draft $K$ 次前向 +
target 验证 $K+1$ 个位置的开销，而"首 token"只等第一个。

### 10.1 三个"算错就静默出错"的地方

- **回传元素数**：投机时是 `width × 请求数`（**元素数**），不是请求数。
  算错只会拿到前 1 个 ⇒ **接受长度被钳到 1，收益全部消失**；
- **定宽 pad**：`width = max(K)+1` 必须两端一致（`_spec_verify` 与 `_update_spec_batch` 的切片）；
  pad 位填 **−1**（不等于任何真实 token，贪心判定会自然停下）；
- **这一步不拉新 prefill**：普通 prefill 每序列只回传 1 个样本，混进来会让定宽切片整体错位。

### 10.2 KV 账本（最容易讲错的一处）

```
写进 KV 的： [ last ][ d₁ d₂ d₃ … d_K ]        ← K+1 个（第 ④ 阶段就写完了）
有效的：     [ last ][ d₁ … d_j ][ 修正 token ]  ← j+1 个
账本只推进 j+1；剩下 K−j 个 slot **不回收、不搬家**，留在同一页里，
下一步的写入会自然覆盖（block_manager.may_append_n）。
```

⚠️ **空草稿 ≠ 全被拒**：`propose` 返回 `[]` ⇒ `n_new = 1` ⇒ 这一轮**完全退化成普通 decode**
（连验证前向都不用多跑）。而"草稿全被拒"是把 $K+1$ 个位置**真算了一遍**。

### 10.3 ⚠️ 两个必须主动说清的边界

| 边界 | 说法 |
|---|---|
| **引擎路径的接受判定是贪心** | `_update_spec_batch` 用的是 `greedy_accept_length`（比 token）。`min(1,p/q)` + `(p−q)⁺` 那套在 `spec/verify.py` 里有完整实现与单测，**但没有接进调度器这条路** —— 被追问"采样时怎么办"时要说清这个边界 |
| **"逐 token 等价"是有前提的** | 只在 **top-2 logits 间隔 > 数值误差**时成立。自然散文上实测到过**完全并列**（`13@+20.250` 与 `11@+20.250`）：bf16 下 logits ≈ 20 的 ULP 是 0.125，两个 attention kernel 的累加顺序差异足以把它们舍入成同一个值，`argmax` 就翻转了。⇒ **用"逐 token 相同"验收时必须选 top-2 间隔大的文本**，否则会把数值并列误判成实现 bug |

## 11. 最容易记错的五点

1. **`RF` 是"先 decode、后 prefill"**，回写也是同序 —— 两边共用同一个 `ScheduledBatch`，顺序不一致就会"token 与序列对错位"。
2. **`AT5`（写 KV）在 `AT6`（选路径）之前**：新 token 的 K/V 先写进池子，注意力才能从整池读。
3. **`S4` 只推进 `j+1`**：验证时写进 KV 的是 $K+1$ 个位置，只有前 $j+1$ 个是真的，多写的 $K-j$ 个 slot 不回收、不搬家，靠下一步覆盖。
4. **`16×128 = 2048 ≠ hidden 1024`**：注意力是升维的；`head_dim` 是 config 显式给的 128。
5. **两套缓存并存**：KV 池（随长度涨，4096 上下文 448 MiB/条）+ 块账本（纯 Python 整数列表，不在显存里）。

**两对容易混的概念**：

| | CUDA Graph 的 pad 槽 | 投机的多余槽 |
|---|---|---|
| 怎么来的 | `_pad_bs` 把 batch 补到固定形状 | 验证写了 $K+1$ 个，只接受 $j+1$ 个 |
| `slot_mapping` | **−1**（从来没写过） | 真实槽位（**真写过**） |
| KV 里留下什么 | 什么都没写 | 被拒草稿的 K/V |
| 靠什么恢复 | 不需要 | 下一步的写入覆盖它 |

| | chunked prefill | 投机验证 |
|---|---|---|
| 分什么 | 一条长 prompt 拆成多次 **forward** | **一次** forward 里的 $K+1$ 个 query |
| 输入 | 真实 token | 草稿猜的 token |
| 出口 | 只取最后一个位置 | 每个位置都要比 |
| 本项目 | **没有**（超预算的请求被整条延期，不切片） | 有 |

### 12.0 改图时必须守的四条设计约定

1. **主图只装数据流**：引擎层 + 四张卡各自的流程 + 卡间通信。
   **说明性的内容（投机证明 / 并行轴对照 / 缓存 / 符号表）一律放 `notes.mmd`**，
   不要再往主图里塞 —— 上一版就是这么把主图撑到 130 节点、9 个子图的。
2. **每一格上下两行**：上行 `\text{}` 写「这一步在干什么」，下行写等式（带维度）。
   照 `InfiniLM .../tp_pp_4gpu.html` 的排版。**没有公式的格子也要用 `\text{}` 分两行**，风格要统一。
3. **卡号只写在列标题**：`卡 0 · 段 0 · TP rank 0（跑层 0–13；负责 Q 头 0–7、KV 头 0–3）`。
   **格子里面不要再缀「卡 0 ·」** —— 一列就是一张卡，读者看得见。
4. **多卡要真的看见四张卡**：四列并排，每列一张卡自己的一整条流程。

`check_flow.py --fix-bold` 可一键把 `**粗体**` 换成 `【】`。
`probe_clusters.py` 需要先渲染过一次（用 `_rendered.svg`），它复刻 mermaid 的「第一次提到」归属语义，
**专抓"通信节点没进通信框"这类归属缺陷**（见 §12.1 第一条）。

### 12.1 写这张图时必须知道的 mermaid 规则

- 🔴 **`\begin{gathered}` 的换行要写 4 个反斜杠 `\\\\`，不是 2 个。**
  mermaid 会把 `\\` 反转义成 `\`，所以源码里写 `\\` 到了 KaTeX 手上就变成 `\h`、`\t` 这类**未定义命令**，
  直接报 `KaTeX parse error: Undefined control sequence`。
  规律：**源码里 N 个反斜杠 → KaTeX 收到 N/2 个**。
  所以 `\\\\`（4 个）= KaTeX 的一行换行；`\\\\\text{…}`（5 个）= 换行 + `\text`。
  - 正确：`$$\begin{gathered}\text{第一行}\\\\\text{第二行}\\\\\alpha+\beta\end{gathered}$$`
  - 错误：`…\text{第一行}\\h\,[N,hs]=…` ← 会被当成 `\h`
- 标签里出现 `$$…$$` 后，**mermaid 不再处理 `<br/>`**（`\n`、`<span>` 也无效）
  ⇒ 含公式的格子必须靠 `gathered` 自己分行，**不能混用 `<br/>`**；
- 形状宽度按标签量，但 **mermaid 量高度时没算 KaTeX 墨迹** ⇒ 靠图首 `%%{init: …}%%` 的 `themeCSS`
  给 `.nodeLabel` **和** `.edgeLabel` 的块级子元素补 `padding`，并把 `.katex` 字号调成 `1em`。
  **实测用 `padding: 8px 12px`** —— 4px 时 `gathered` 行数多的格子会有 1–2 px 被裁；
- 六边形 `{{…}}`、圆角 `([…])` 对含公式的标签不可靠（形状比文字窄、或吞掉换行）
  ⇒ 集合通信节点用**矩形 + `classDef` 配色**；
- 标签里不能用 `{}` 当普通字符（`$$…$$` 内的花括号安全）。
- ⚠️ **`**粗体**` 在这个渲染配置下不生效 —— 会原样显示成 `**分工**`**。
  要找强调效果就用 `【】`。实测 38 处 `**…**` 全部原样吐出，换成 `【】` 后正常。
- 🔴 **节点的子图归属按「第一次提到」判定 —— 通信子图必须写在卡片子图之前。**
  这是本项目真实踩过的坑（表现为"只有第一次 allreduce 进了组内通信框"）：
  `X1`/`X2` 的**首次提到**是 `subgraph C0` 里的边 `C0h --> X1`，
  而 `subgraph TPA` 的声明在更后面 ⇒ `X1`/`X2` 被判给**根图**。
  渲染出来它们的位置其实是对的（被上游边拉到了该在的深度），
  但 `TPA` 的框只围住了在 TPA 里首次出现的 `X0` —— 看起来就是"没放进框里"。
  - 症状：子图框只框住**第一个**成员，其余成员散在框外；
  - 修法：把 `subgraph TPA` / `subgraph TPB`（以及独立的 `X3`/`X4`）
    **挪到 `subgraph C0` 之前**，让每个通信节点的首次提到落在自己的子图里；
  - 顺带好处：画布宽 2208 → **1955**，最长边 1239 → **726**；
  - 回归检查：`python probe_clusters.py full_flow.mmd _rendered.svg`
    （复刻"第一次提到"语义算出成员表，再查每个成员是否落在自己的框内）。
    拿修复前的图源跑会报 `TPA 成员 1/1` 并把 `X1`/`X2` 标成越框 —— 正是这个缺陷的指纹。
- 🔴 **不要制造"平行边"**：如果写 `A --> B --> C --> …`，同时又有 `B --> X --> C`，
  那 `B→C` 就多了一条直连边，必然和 `B→X→C` 交叉。
  正确写法是把链拆开：`A --> B` 然后用 `B --> X`、`X --> C` 接上。
- ⚠️ **不要制造环**（例如把末尾的回传边连回最上面的框）：会让 dagre 排布错乱、子图框互相压。
  闭环用文字说明即可。
- 💡 **没有边的节点会被并排放在同一行**，把画布撑得很宽 ⇒ 用**不可见连线 `~~~`** 串成一列
  （不画线、只影响排布）。`notes.mmd` 的四个说明块就是这么收成一列的。
- 💡 **相邻两列的子图框只差 1–2 px 是正常的**。渲染度量已把子图框向内缩 2 px 再算重叠，
  所以「贴边」不会误报成重叠缺陷。

### 12.2 三条环境坑（都踩过）

1. **`chrome.exe` 是 GUI 子系统程序，stdout 抓不到** ⇒ 不能用 `--dump-dom` 收结果；
   所有产物一律让页面 `POST /save?name=…` 落盘；
2. **不要加 `--virtual-time-budget` 跑渲染**：虚拟时间会饿死 mermaid 的异步渲染
   （表现为 `mermaid.render` 永不返回、`_status.json` 不生成）。改成后台起真实时间的 Chrome，
   **轮询 `_status.json`** 再 kill（截图可以用 `--virtual-time-budget`，那是静态页）；
3. **`.ps1` 必须 ASCII-only**：本机 Windows PowerShell 按 ANSI 代码页（GBK）读脚本，
   UTF-8 无 BOM 的中文注释会吞掉后面的换行或引号。
   同理 `_metrics.json` 是 UTF-8，Windows PowerShell 5.1 的 `Get-Content` 会按 GBK 读坏
   ⇒ 脚本里用 `Read-Json` 显式按 UTF-8 解码。

### 12.3 标签被"吞"的根因与三层修法

现象：查看器里有些方框的最右侧符号被**整齐切断**（切在框的右边缘上）。

根因：**框宽是导出那一刻量出来的**，被冻进 `foreignObject` 的 `width`；显示时的度量比它宽就会被裁。
两件事叠加：① KaTeX 的 `@font-face` **懒加载**，`document.fonts.ready` 在还没有文本用到它时就 resolve
⇒ mermaid 拿**回退字体**的宽度定框；② `foreignObject` 默认 `overflow:hidden` ⇒ 超出部分被整齐切掉。

修法（三层，缺一不可）：

1. `render_page.html`：`mermaid.render` **之前** 强制加载全部字体面
   `await Promise.all([...document.fonts].map((f) => f.load().catch(() => null)))`；
2. 导出时**直接往 SVG 里注入** `<style>foreignObject{overflow:visible}</style>`
   （写进 themeCSS 无效 —— mermaid 会把选择器整体小写成 `foreignobject`，SVG 标签名区分大小写）；
3. 查看器模板按**本浏览器的真实字宽**把超框标签缩回框内（只动标签、不动几何，不会造成节点重叠）。
